# Content and Accessibility

## Voice

- Write in a warm, direct, curious first person where personal context helps.
- For projects, lead with the problem and purpose, then explain the approach and the current state.
- Prefer concrete, plain-language descriptions over hype, buzzword stacks, or unsupported superlatives.
- Keep technical depth available in details, diagrams, and links without making the first read feel like an interview transcript.
- Preserve the user's personal theme of vitality, curiosity, perseverance, and care for nature without forcing it into every heading.

## Accuracy

- Treat project PDFs as context, not proof that every described feature or metric is implemented.
- Preserve the difference between completed, active, planned, and unverified work.
- For new studies without public repositories, say so plainly instead of using a `#` link or a disabled-looking fake button.
- Do not promise that contact forms send messages unless a working service is configured. Offer a real mail link or an honest email-draft flow.

## Accessibility and responsive behavior

- Use semantic headings, landmarks, lists, links, buttons, and native `details`/`summary` where they fit.
- Provide descriptive alternative text for informative imagery; mark decorative imagery as decorative.
- Keep focus visible, contrast readable, and controls usable by keyboard and touch.
- Give videos controls and fallback text. Only use approved poster images; MorningTide uses its demo video without an illustrated poster.
- Announce filter-result changes where appropriate and keep the current filter state available to assistive technology.
- Honor `prefers-reduced-motion`; never make essential content depend on animation.
- Check layout at narrow widths and avoid relying on hover alone.
